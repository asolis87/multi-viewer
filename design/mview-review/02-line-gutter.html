      mview — CLI viewer for Markdown, Mermaid and JSON

      Local CLI (mview) that opens the browser on a 127.0.0.1 server and renders Markdown (with embedded Mermaid), Mermaid and JSON from a file, the clipboard or stdin. Node + TypeScript CLI, Svelte frontend bundled into the package. v0.1 MVP = S1–S8; anything else (tabs, YAML, daemon reuse) is out of scope.

        • Command. When the first argument is review it is a subcommand (like skill, S12); mview ./review opens a file named review. mview review <file> takes exactly one file; none or more than one exits 2 with mview: review takes one Markdown file. The file is validated as S2 (same file not found / not a file errors, exit 1). Markdown only (L81): a file whose type by S4's extension rule is not markdown (.md, .markdown, or no known extension) exits 1 with mview: review needs a Markdown file: <file>. Piped stdin is not read. --port, --no-open and --auto-close work as today; --paste, --detach and --no-auto-close exit 2 with mview: review takes a file and waits for the decision (agents run it as a background command instead of --detach). It starts a server on the file, opens the browser and waits until the human submits. Both startup lines, mview: <url> and Press Ctrl+C to stop., go to stderr, so stdout carries only the result. Ctrl+C stops it as today and prints nothing on stdout.
        • Result: stdout only (L84). On submission the CLI writes the result to stdout and exits; it writes no file (to keep one: mview review plan.md > plan.review.md). Exit codes: 0 approved, with or without comments; 3 changes requested; 4 no decision — every page closed under S11's rules (10 s after the last page, 60 s if none opened) without a submission, printing mview: review closed without a decision on stderr and nothing on stdout; 1 and 2 as today. The result is Markdown, comments in document order (by start line, then creation order):

          Decision: is approved, approved_with_comments or changes_requested. Each heading names the kind (Change request, Answer, Note) and the 1-based source lines (line N or lines N–M) as captured when the comment was made. The quote is the selected text with > before each of its lines, omitted when the comment is on whole blocks. The comment text follows as typed, except that a line starting with # gets a \ before it so it cannot end the comment's section.
        • Review page (contract). Doc gains review?: true, set only by servers started by mview review. Only such pages show the review UI and carry source line attributes; every other page, including the normal Markdown view (S15), is unchanged.
        • Anchoring: free selection, block anchor (L82). On a review page each rendered block carries its 1-based, inclusive source line range from markdown-it's token.map: paragraphs, headings, list items, blockquotes, table rows, code blocks and fenced Mermaid diagrams. Selecting text inside one block anchors to the innermost block that contains the whole selection (in a nested list, the inner item); the quote is the selected text, trimmed, at most 500 characters, and its first occurrence in that block is highlighted. A selection across several blocks anchors from the first block's start line to the last block's end line, keeps the quote for the result, and highlights each of those blocks whole. A block's comment control, used without a selection, comments on the whole block with no quote. Character-offset anchoring is out of scope (L81).
        • File changes during a review (L84). Live reload (S2) still shows the new content. Comments keep their line ranges and quotes as captured (no re-anchoring); their highlights are drawn on blocks with the same line range when one exists, otherwise the comment shows only in the panel. From the first change on, the notice The file changed; line numbers may not match stays visible until submission.
        • Comments. Kinds: Change request (default), Answer (for open questions; no automatic question detection, L82) and Note. The text is required (not blank). Several comments may share a block. A side panel lists them in document order with kind, lines and quote; clicking one scrolls to its block and marks it; each can be edited or deleted. Drafts live in the tab's sessionStorage under the run token: they survive a reload of that tab, are not shared with other tabs, and are cleared on submission (L84).
        • Staying open. A review page never closes its event stream because it is hidden: S14's 30-minute rule does not apply to review pages. Closing every tab still follows S11 and ends with exit 4.
        • Submitting. Two buttons: Request changes (enabled with at least one comment) and Approve, labelled Approve with comments when there are comments (L82). No confirmation. When the server accepts, it sends event: submitted to every open page of the run before stopping; every such page becomes read-only and shows Review sent — you can close this tab instead of its status text, and keeps it after the server stops (instead of S14's Stopped).
        • Server. Only a review server has POST /api/review?t=<token>. Checks run in this order, and the first that fails answers: allowed Host (403, as every route); method — /api/review accepts only POST, every other route only GET/HEAD (405); token (403); Origin equal to http:// plus the request's Host (403); Content-Type: application/json (415); body at most 256 KB (413); not submitted yet (409); body valid (400 with { error } naming the reason). On other servers nothing changes: a POST anywhere gets 405 as today (S3 still holds) and GET /api/review gets 404. A valid body is { decision, comments: [{ kind, startLine, endLine, quote?, text }] } where decision is approved, approved_with_comments or changes_requested; kind is change, answer or note; lines are integers ≥ 1 with startLine ≤ endLine; text is not blank; quote, when present, is at most 500 characters. approved must have no comments; the other two decisions need at least one. Accepted → 200 { ok: true }, then the submitted event, then the CLI writes the result and exits. The CSP is unchanged (connect-src 'self' allows the fetch; form-action 'none' stays).
        • Agent skill. The skill (S12) gains a section: when the human should review a plan or spec, write it to a .md file, run mview review <file> as a background command, give the human the mview: <url> line from stderr, and when it exits read stdout. 0 → continue with the step that was already authorized, applying any comments; 3 → revise the same file and run mview review again; 4 → ask the human in the chat. The decision answers that document only; it grants nothing else (no publishing, no unrelated work). --help and the README describe review.
        • Design first (S9). Artboards under design/mview-review/ show the review mode on this document before code: selecting text, the comment popover with the three kinds, the comments panel, the file-changed notice, the two buttons, and the sent state, in light and dark; the user picks one.
        • Out of scope. Other document types, character-offset anchoring, re-anchoring after file changes, writing the result to a file (L84), replies or threads, several reviewers, editing the document from the page.
        • Check. Unit tests: line ranges per block type (including nested list items and table rows), the innermost-block and multi-block rules, result formatting (multi-line quotes, # lines in text), and each server status in the order above. CLI tests through the public command: exit codes 0, 3 and 4 with exact stdout and stderr, every usage error above, a non-Markdown file, and that a server started without review answers 405 to POST /api/review and 404 to GET /api/review. A headless browser check selects text, adds one comment of each kind, edits and deletes one, reloads the tab and still sees the drafts, submits, and sees the sent state; a non-review page has no line attributes.

      Server contract (shared by CLI and frontend)

      • GET / → frontend index.html; static assets under /assets/*. These carry no document data and do not require the token.
      • Token delivery: the CLI prints and opens /?t=<token>; the frontend reads it from location.search. Without a token, or with an invalid one, the page shows "This page needs the link printed by mview".
      • GET /api/doc?t=<token> → Doc = { name: string|null, type: "markdown"|"mermaid"|"json"|"csv", content: string, source: "file"|"paste"|"stdin"|"empty" }; read failure → 500 { error: string }.
      • GET /api/events?t=<token> → SSE; emits event: change when the watched file changes. The token goes in the query string because EventSource cannot set headers.
      • POST /api/review?t=<token> → only on servers started by mview review (S17), with the check order of S17; on other servers POST gets 405 as on every route and GET /api/review gets 404. Doc.review?: true marks a review page (S17).
      • Only /api/* requires the token: missing/wrong → 403. Every route accepts exactly Host: 127.0.0.1:<port> and Host: localhost:<port>, compared case-insensitively as HTTP requires (T14); any other value (including the host without a port, or [::1]) gets 403 (DNS-rebinding guard). Unknown path → 404.
      • Shared code lives in src/shared/: detect.ts (detectType(content, filename?), firstMeaningfulLine — T13) and doc.ts (Doc, DocSource, empty doc). Both CLI and frontend import them; neither redefines them.
